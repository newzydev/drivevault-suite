## 1. เป้าหมายและขอบเขต

โปรแกรม Windows แบบ native (C++20, Qt 6.8 / Qt Quick, CMake เหมือนโปรแกรมอื่นในชุด ไม่ใช้ Electron / Tauri / WebView) สำหรับ **ดูและควบคุมหน้าจอ Windows อีกเครื่องจากระยะไกล** แบบเดียวกับ AnyDesk / TeamViewer

### ความสามารถที่อยู่ในขอบเขต (ทำตามเฟสในหัวข้อ 5)
1. เครื่องที่ถูกควบคุม (Host) มี **เลขประจำเครื่องที่ไม่เปลี่ยน** (สร้างตอนติดตั้ง/เปิดครั้งแรก) และ passcode ใช้ครั้งเดียวที่เปลี่ยนทุกครั้ง หรือรหัสผ่านถาวรที่ผู้ใช้ตั้งเอง (ใช้รหัสผ่านถาวรแล้วไม่ต้องกรอก passcode) เครื่องที่ควบคุม (Viewer) กรอกเลข + รหัสเพื่อเชื่อมต่อ ผ่านได้ทุกเครือข่าย (ผ่านเซิร์ฟเวอร์ของเจ้าของ ดู 3.3)
2. ดูหน้าจอแบบสด (รองรับหลายจอ เลือกจอได้) ควบคุมเมาส์และคีย์บอร์ดจาก Viewer
3. คลิปบอร์ดข้อความ สองทาง
4. ส่งไฟล์ระหว่างสองเครื่อง (ผู้ใช้กดเองทุกครั้ง)
5. เสียงจากเครื่อง Host (ภายหลัง)
6. การเชื่อมต่อเข้ารหัสปลายทางถึงปลายทาง (end-to-end) ขอความยินยอมทุกครั้งที่มีคนเข้าควบคุม
7. เข้าถึงโดยไม่มีคนเฝ้า (unattended) ด้วยรหัสผ่านถาวรที่ตั้งเอง (เฟสท้าย ต้องติดตั้งเป็น Windows service)

### ตัดออกจากขอบเขต (ตัดสินใจแล้วจนกว่าเจ้าของจะเปลี่ยน)
- **โหมดซ่อนตัว / ไม่แสดงให้เจ้าของเครื่องเห็น**: ไม่ทำเด็ดขาด (เสี่ยงเป็นเครื่องมือสอดแนมและหลอกลวง) Host ต้องมีสัญลักษณ์ชัดเจนตลอดเวลาที่ถูกควบคุม และตัดการเชื่อมต่อได้ทันที
- macOS / Linux / มือถือ (ชุดนี้เป็น Windows เท่านั้น เก็บไว้เป็นความคิดอนาคต)
- บัญชีผู้ใช้ รายชื่อเครื่อง คลาวด์ การประชุมหลายคน การบันทึกวิดีโอเซสชัน (ยังไม่ทำ)
- การส่งภาพหน้าจอ/อินพุตผ่านบริการของบุคคลที่สาม (ไม่ฝากข้อมูลหน้าจอไว้ที่ใครนอกจากเซิร์ฟเวอร์ของเจ้าของเองซึ่งส่งต่อได้เฉพาะข้อมูลที่เข้ารหัสปลายทางถึงปลายทาง ดู 3.3) ข้อยกเว้นอย่างเดียวที่เสนอกับบุคคลที่สาม: ถามเซิร์ฟเวอร์ STUN สาธารณะเพื่อรู้ที่อยู่ภายนอกของตัวเอง STUN ไม่เห็นและไม่ส่งต่อข้อมูลเซสชัน

จุดต่างที่ตั้งใจ: ไม่มีบัญชี ไม่มีโฆษณา ภาพหน้าจอไม่ผ่านเซิร์ฟเวอร์กลางแบบอ่านได้ (เข้ารหัสปลายทางถึงปลายทาง) และเป็นชุดเดียวกับโปรแกรม DriveVault อื่น

## 2. หลักการที่ต้องยึด (ตรงกับกฎของชุด)
- **ซื่อสัตย์**: สถานะบนการ์ดต้องตรงความจริง (เร็วๆ นี้ / ยังไม่พร้อม / พร้อมใช้) ไม่ทำฟีเจอร์ปลอม
- **ออฟไลน์ก่อน**: ไม่ดาวน์โหลดหรือเชื่อมต่ออะไรเองตอนเปิดโปรแกรม เครือข่ายทำงานเมื่อผู้ใช้กดเริ่มแชร์หรือกดเชื่อมต่อเท่านั้น
- **ความยินยอม**: ทุกเซสชันแรกต้องให้เจ้าของเครื่อง Host กดอนุญาต (ยกเว้นโหมด unattended ที่เจ้าของเปิดเองและเห็นป้ายแจ้งตลอด)
- **ไม่เก็บรหัส**: รหัสผ่านและรหัสเชื่อมต่อไม่ถูกเขียนลง log และไม่เก็บเป็นข้อความธรรมดา
- **ไลเซนส์**: ใช้เฉพาะ MIT / BSD / Apache-2.0 / LGPL (ผ่าน DLL) ห้าม GPL / AGPL (เช่น x264 เป็น GPL ใช้ไม่ได้) ต้องผ่าน license audit ของ `package.ps1`
- **ทดสอบเงียบและไม่แตะเครื่องเจ้าของ**: เทสต์ใช้ loopback บนเครื่องเดียว ไม่ควบคุมเมาส์/คีย์บอร์ดจริงของเจ้าของ ไม่เล่นเสียง (`DV_NO_AUDIO=1`)

## 3. สถาปัตยกรรมที่เสนอ

```
apps/drivevault-remote-desktop-pro/
  src/capture/   จับภาพหน้าจอ (DXGI Desktop Duplication) - ที่เดียวที่แตะ API จับภาพ
  src/codec/     บีบอัด/คลายภาพ (Media Foundation H.264 ฮาร์ดแวร์ + ตัวสำรอง) - ที่เดียวที่แตะตัวเข้ารหัส
  src/input/     ฉีดเมาส์/คีย์บอร์ดด้วย SendInput (Host) และจับอินพุต (Viewer)
  src/net/       การเชื่อมต่อ: โปรโตคอลข้อความ, เข้ารหัส, ค้นหาเส้นทาง (LAN / relay)
  src/session/   เครื่องสถานะเซสชัน: จับคู่ ยินยอม เริ่ม หยุด
  src/app/       main.cpp, Host controller, Viewer controller
  src/ui/        QML: หน้า Host, หน้า Viewer, ป้ายแจ้ง "กำลังถูกควบคุม"
  service/       (เฟสท้าย) Windows service สำหรับ unattended และหน้าจอ UAC / ล็อกอิน
  tests/         Qt Test บน loopback + fake capture
```

### 3.1 จับภาพ
- DXGI Desktop Duplication: ส่งเฉพาะบริเวณที่เปลี่ยน (dirty rects) ลดแบนด์วิดท์ (ต้องตรวจ: ใช้ได้กับ GPU ทั้งหมดของเครื่องทดสอบ รวมโน้ตบุ๊กที่มี GPU สองตัว)
- ตัวสำรองเมื่อ DXGI ไม่ได้ (เช่น เซสชัน RDP, บางไดรเวอร์): Windows.Graphics.Capture หรือ GDI แบบช้า (ต้องตรวจ)
- เคอร์เซอร์ส่งแยกจากภาพ เพื่อให้เมาส์ลื่นแม้ภาพช้า

### 3.2 บีบอัดภาพ
- ตัวหลัก: H.264 จาก Media Foundation (ฮาร์ดแวร์เมื่อมี) ไม่ต้องแถมตัวเข้ารหัสที่เป็น GPL (ต้องตรวจ: คุณภาพ/ความหน่วงบนเครื่องทดสอบ และเงื่อนไขสิทธิบัตรของ H.264 สำหรับการแจกจ่าย)
- ทางเลือก: VP8/VP9 ด้วย libvpx (BSD-3, ไม่มีค่าสิทธิบัตร แต่ซอฟต์แวร์เข้ารหัสกินซีพียูมากกว่า) ตัดสินใจหลังวัดจริงในเฟส 0
- ปรับคุณภาพ/เฟรมเรตตามแบนด์วิดท์ที่วัดได้ มีโหมด "ข้อความคมชัด" สำหรับงานเอกสาร

### 3.3 เครือข่ายและความปลอดภัย (ส่วนที่เสี่ยงที่สุด)
- **การเข้ารหัส**: TLS 1.3 หรือ Noise protocol (QSslSocket / Schannel; ต้องตรวจว่าตัวไหนผ่านกฎไลเซนส์และใช้งานง่ายกว่า) พร้อมยืนยันตัวกันด้วยรหัสที่แชร์ (PAKE เช่น SPAKE2 / OPAQUE หรือรหัสใช้ครั้งเดียวผูกกับลายนิ้วมือใบรับรอง) เพื่อกันคนกลาง
- **ตัวตนของเครื่องและรหัส (ตามที่เจ้าของต้องการ 2026-11-17: ติดตั้งแล้วมีเลขประจำเครื่องที่ไม่เปลี่ยน ส่วน passcode เปลี่ยนทุกครั้ง และตั้งรหัสผ่านถาวรได้)**:
  - **เลขประจำเครื่อง**: สร้างครั้งเดียวตอนเปิดโปรแกรมครั้งแรกหลังติดตั้ง แล้ว **ไม่เปลี่ยน** เป็นเลข 9-10 หลักที่คำนวณจากกุญแจสาธารณะของเครื่อง (กุญแจคู่ Ed25519 เก็บเข้ารหัสด้วย Windows DPAPI) เซิร์ฟเวอร์ตรวจว่าไม่ชนกันตอนลงทะเบียนครั้งแรก เลขไม่ใช่ความลับ (เดาและสแกนได้) จึงต้องมีรหัสและการยินยอมเสมอ ติดตั้งใหม่หรือย้ายเครื่อง = กุญแจใหม่ = เลขใหม่ เว้นแต่จะมีการส่งออก/นำเข้ากุญแจ (เฟสหลัง) การโคลนดิสก์ทั้งก้อนทำให้เลขซ้ำ ต้องตรวจและให้สร้างใหม่ (ต้องตรวจ)
  - **passcode ใช้ครั้งเดียว**: สุ่มใหม่ทุกครั้งที่ Host เริ่มรับการเชื่อมต่อและหลังถูกใช้หนึ่งครั้ง หมดอายุเร็ว สั้นพอพิมพ์ได้ (เช่น 6-8 หลัก) ปลอดภัยพอเพราะใช้ PAKE และจำกัดครั้งที่ลองผิด
  - **รหัสผ่านถาวร (ผู้ใช้ตั้งเอง)**: ถ้า Viewer ใช้รหัสผ่านถาวร ก็ไม่ต้องกรอก passcode เก็บเป็นตัวตรวจสอบ (salt + hash ช้า หรือ verifier ของ PAKE) ไม่เก็บข้อความจริง ปิดไว้เป็นค่าเริ่มต้น ตั้ง/เปลี่ยน/ปิดได้ เตือนรหัสอ่อน จำกัดครั้งผิดและหน่วงเวลา ป้ายแจ้งถูกควบคุมแสดงเสมอ (การเข้าด้วยรหัสผ่านถาวรโดยไม่ต้องกดยอมรับที่เครื่อง Host ให้เจ้าของเลือก หัวข้อ 7)
- **เส้นทาง: ผ่านเซิร์ฟเวอร์ของเจ้าของที่ออนไลน์และใช้งานอยู่แล้ว (เจ้าของแจ้ง 2026-11-17: มีเครื่อง server ใช้งานอยู่ โค้ดอยู่คนละ repo / คนละโปรเจกต์)** เลขที่ไม่เปลี่ยนและต่อได้ทุกเครือข่าย **ต้องมีเซิร์ฟเวอร์** เพราะต้องมีที่จำว่าเลขไหนอยู่ที่ไหนตอนนี้ และต้องส่งต่อข้อมูลเมื่อเจาะ NAT ไม่ได้ จึงมี 3 ระดับ
  1. **LAN / ที่อยู่ IP ตรง**: ไม่ต้องใช้เซิร์ฟเวอร์ ทำก่อน
  2. **ผ่านเซิร์ฟเวอร์ (ไดเรกทอรี + สัญญาณ) แล้วเจาะต่อเป็นการเชื่อมต่อตรง**: Host เปิดการเชื่อมต่อขาออกคงไว้กับเซิร์ฟเวอร์ (TLS/WebSocket) พร้อมลงทะเบียนเลข Viewer ส่งเลขไปที่เซิร์ฟเวอร์ เซิร์ฟเวอร์ส่งสัญญาณถึง Host แล้วทั้งสองฝั่งลองเจาะ NAT ตรง (STUN + UDP hole punching) ถ้าได้ ข้อมูลเซสชันไปตรงระหว่างสองเครื่อง
  3. **relay ผ่านเซิร์ฟเวอร์** เมื่อเจาะไม่ได้ (CGNAT, NAT แบบ symmetric, บล็อก UDP): เซิร์ฟเวอร์ส่งต่อข้อมูลที่เข้ารหัสปลายทางถึงปลายทางแล้ว อ่านไม่ได้ ทำให้ต่อได้ทุกเครือข่ายที่ออกอินเทอร์เน็ตได้ (ประมาณช้ากว่าและกินแบนด์วิดท์เซิร์ฟเวอร์)
- **สิ่งที่ต้องเขียนให้ตรงความจริง**:
  - เซิร์ฟเวอร์เห็นเมทาดาตา (เลขเครื่อง, IP ที่เชื่อมต่อ, เวลา, ปริมาณข้อมูล) แต่ไม่เห็นภาพหน้าจอและอินพุต เพราะเข้ารหัสปลายทางถึงปลายทาง ต้องบอกผู้ใช้ในข้อความความเป็นส่วนตัว
  - Host ต้องเปิดการเชื่อมต่อออนไลน์ค้างไว้ตลอดที่เปิดรับการเชื่อมต่อ จึงเป็นโปรแกรมที่ "ออนไลน์เมื่อผู้ใช้เปิดสวิตช์รับการเชื่อมต่อ" ต่างจากกฎของ Master Pro (ซึ่งยังเป็นกฎของ Master Pro เท่านั้น) ต้องมีสวิตช์ชัดเจน และตัดสินใจว่าเปิดเป็นค่าเริ่มต้นหรือไม่ (หัวข้อ 7)
  - ต้นทุนแบนด์วิดท์ของ relay: วิดีโอหน้าจอราว 1-8 Mbps ต่อเซสชันตามคุณภาพ (ต้องวัดจริง) และสัดส่วนเซสชันที่ต้องใช้ relay ยังไม่ทราบ (ต้องตรวจ)
  - เซิร์ฟเวอร์ปัจจุบันเข้าถึงอินเทอร์เน็ตผ่านบริการอุโมงค์แบบ Tailscale Funnel (ตามภาพที่เจ้าของส่งมา) ซึ่งโดยทั่วไปเป็น TCP/HTTPS ไม่ใช่ UDP และอาจมีเพดานแบนด์วิดท์ จึง **ต้องตรวจก่อนสัญญา**: relay ผ่าน WebSocket/TCP ได้หรือไม่ ช้าแค่ไหน หรือต้องเปิดพอร์ต UDP/ใช้ที่อยู่สาธารณะแยกสำหรับ relay
  - โค้ดฝั่งเซิร์ฟเวอร์อยู่ **อีก repo หนึ่ง** งานนี้ไม่แก้ repo นั้นจนกว่าเจ้าของสั่ง สัญญาโปรโตคอลระหว่างโปรแกรมกับเซิร์ฟเวอร์ (การลงทะเบียนเลข, สัญญาณ, relay, หมายเลขเวอร์ชันโปรโตคอล) เขียนเป็นเอกสารกลางเอกสารเดียวในโฟลเดอร์ `docs` ของชุดนี้ก่อน แล้วให้ทั้งสอง repo ทำตาม (โมดูลไดเรกทอรี/relay ใหม่เพิ่มที่ repo เซิร์ฟเวอร์)
  - ที่อยู่ของเซิร์ฟเวอร์และข้อมูลส่วนตัวของเจ้าของไม่เขียนลงเอกสารหรือโค้ดที่ commit
- **ความปลอดภัยของไดเรกทอรี/relay**: Host ลงทะเบียนด้วยลายเซ็นของกุญแจเครื่อง (เซิร์ฟเวอร์ปลอมเลขของคนอื่นไม่ได้), Viewer ตรวจลายนิ้วมือกุญแจของ Host ผ่านการยืนยันแบบ PAKE (เซิร์ฟเวอร์เป็นคนกลางแล้วถอดภาพไม่ได้), จำกัดอัตราการลองเลข/รหัสต่อ IP และต่อเลข, เซิร์ฟเวอร์ตอบเหมือนกันเมื่อเลขไม่มี/ออฟไลน์เพื่อกันการสแกนว่าเลขไหนออนไลน์ (ต้องตรวจว่าทำได้โดยไม่เสียประสบการณ์ผู้ใช้), เลขถูกบล็อกได้เมื่อมีการร้องเรียนการใช้หลอกลวง (นโยบายเจ้าของ)
- **การป้องกันการหลอกลวง** (สำคัญ เพราะเครื่องมือแบบนี้ถูกใช้หลอกให้โอนเงิน): หน้าต่างแจ้ง "ใครกำลังขอควบคุมเครื่องคุณ" ชัดเจน ป้ายถาวรบนจอขณะถูกควบคุม ปุ่มตัดทันทีและปุ่มลัด ข้อความเตือนให้อนุญาตเฉพาะคนที่รู้จัก ไม่มีโหมดซ่อน รหัสหมดอายุเร็ว ล็อกหลังกรอกผิดหลายครั้ง
- ไม่เก็บภาพหน้าจอหรือเนื้อหาที่ผ่านบนดิสก์ ไม่ log เนื้อหา

### 3.4 ควบคุมอินพุต
- Host ฉีดเมาส์/คีย์บอร์ดด้วย `SendInput` (รหัสปุ่มแบบ scan code เพื่อให้ภาษาไทย/แป้นพิมพ์อื่นถูกต้อง ต้องตรวจ)
- **ข้อจำกัดของ Windows ที่ต้องบอกผู้ใช้ตรงๆ**: โปรเซสผู้ใช้ทั่วไปควบคุมหน้าต่างที่รันแบบผู้ดูแล (UAC), หน้าจอล็อก และหน้าจอล็อกอินไม่ได้ การรองรับต้องใช้ Windows service รันเป็น SYSTEM และจับ secure desktop (งานยากและเสี่ยง ทำเฟสท้าย) ก่อนถึงตอนนั้นโปรแกรมต้องแจ้งว่าไม่รองรับ ไม่ทำเป็นว่าใช้ได้
- จำกัดอัตราและตรวจค่าอินพุตจาก Viewer (กันค่าผิดปกติ)

## 5. เฟสพัฒนา (แต่ละเฟสต้อง build + ทดสอบ + commit ก่อนไปเฟสต่อไป)
- **เฟส 0 - ตัดสินใจและทดลองเล็ก**: ให้เจ้าของตอบหัวข้อ 7 วัดจริงบนเครื่องทดสอบ: จับภาพ DXGI, เข้ารหัส H.264 ฮาร์ดแวร์ vs libvpx (ความหน่วง, ซีพียู, คุณภาพข้อความไทย), **ทดลองเจาะ NAT**: เครื่องมือเล็กที่ถาม STUN แล้วลองยิง UDP หากันระหว่างเครือข่ายจริงอย่างน้อย 2-3 แบบ (เน็ตบ้านสองเจ้า, เน็ตมือถือแชร์) เพื่อรู้ว่าระดับ 2 ใช้ได้บ่อยแค่ไหนก่อนลงแรงต่อ, สร้างโปรเจกต์เปล่าที่ build ได้ (CMake, หน้าต่างว่าง, `product.json`)
- **เฟส 1 - ท่อภาพบนเครื่องเดียว**: จับ -> บีบอัด -> คลาย -> แสดง ในหน้าต่างเดียวผ่านซ็อกเก็ต loopback วัดเฟรมเรต/ความหน่วงจริง
- **เฟส 2 - เชื่อมต่อ LAN ที่ปลอดภัย**: โปรโตคอลข้อความ (เวอร์ชัน, keep-alive), จับคู่ด้วยรหัส, เข้ารหัสปลายทาง, หน้าต่างยินยอม, ป้ายแจ้งถูกควบคุม, ปุ่มตัด, ทดสอบการโจมตีพื้นฐาน (รหัสผิด, replay, ตัดกลางทาง)
- **เฟส 3 - ควบคุมและคลิปบอร์ด**: อินพุตสองทาง, หลายจอ, ปรับขนาด/DPI, คลิปบอร์ดข้อความ
- **เฟส 4 - เลขประจำเครื่อง + เซิร์ฟเวอร์ไดเรกทอรี/สัญญาณ**: สร้างและเก็บกุญแจเครื่อง, เลขประจำเครื่องคงที่, passcode ใช้ครั้งเดียว, รหัสผ่านถาวร (verifier ไม่เก็บข้อความจริง), สัญญาโปรโตคอลกลางใน `docs` ของชุดนี้ (มีหมายเลขเวอร์ชัน), โมดูลไดเรกทอรี/สัญญาณที่ repo เซิร์ฟเวอร์ (เมื่อเจ้าของสั่งให้แตะ repo นั้น), เจาะ NAT ตรง (STUN + UDP), ข้อความที่ตรงความจริงเมื่อเจาะไม่ได้, ทดสอบด้วยเครือข่ายจำลอง (NAT หลายแบบ) และเครือข่ายจริง
- **เฟส 4b - relay**: ส่งต่อข้อมูลที่เข้ารหัสปลายทางถึงปลายทางผ่านเซิร์ฟเวอร์เมื่อเจาะไม่ได้ วัดแบนด์วิดท์และความหน่วงจริงของเซิร์ฟเวอร์และช่องทางที่เปิดสู่อินเทอร์เน็ต ตั้งเพดานต่อเซสชัน/ต่อผู้ใช้ และเอกสารการดูแลเซิร์ฟเวอร์
- **เฟส 5 - ส่งไฟล์และเสียง**
- **เฟส 6 - unattended และ service** (ต้องมีเอกสารความเสี่ยงและการทดสอบบนเครื่องสะอาด/VM)
- **เฟส 7 - แพ็กเกจและผสาน Master Pro**: Inno Setup (`AppId` ใหม่ที่ไม่เปลี่ยนอีก), registry `Software\DriveVault\Products\RemoteDesktopPro`, `product.json`, ตัวติดตั้งพก/รันติดตั้ง Master Pro ก่อนตามสัญญา, release gates (clean-machine, license audit, notices), รายการตรวจเครื่องสะอาด

## 7. สิ่งที่ต้องให้เจ้าของตัดสินใจก่อนเริ่มเฟส 4 (เฟส 0-3 เริ่มได้เลย)

2. **ตัวเข้ารหัสวิดีโอ**: H.264 ผ่าน Media Foundation (ง่าย เร็ว แต่ประเด็นสิทธิบัตรเมื่อแจกจ่าย ต้องตรวจ) หรือ VP8/VP9 (libvpx, ไม่มีค่าสิทธิบัตร กินซีพียูมากกว่า)
3. **หมวดบนการ์ด**: ตอนนี้วางตามที่เจ้าของชี้ไว้ (หมวดมัลติมีเดีย) ต้องการหมวดใหม่ เช่น "เครือข่าย / ยูทิลิตี้" หรือไม่
4. **สี accent**: ใช้ `#06B6D4` ตามที่เสนอ หรือเลือกสีอื่น
5. **ขอบเขตแรก**: ต้องการ unattended access (service) ในรุ่น 1.0 หรือรอรุ่นถัดไป
6. **ใช้งานกับใคร**: ใช้เองกับเครื่องของตัวเอง หรือแจกให้คนทั่วไป (แจกทั่วไปต้องใส่ใจเรื่องการใช้ในทางหลอกลวง การลงนามรหัส และข้อความ EULA เพิ่ม)

## 9. สิ่งที่ยังไม่ได้ตรวจ (ต้องตรวจก่อนสัญญากับผู้ใช้)
