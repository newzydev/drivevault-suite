## 1. เป้าหมายและขอบเขต

โปรแกรม Windows แบบ native (C++20, Qt 6.8 / Qt Quick, CMake เหมือนโปรแกรมอื่นในชุด ไม่ใช้ Electron / Tauri / WebView) ที่ **ทำงานในเครื่อง ไม่อัปโหลดไฟล์ไปที่ไหน**
เปิดอ่านและจัดการ PDF ได้ครบเรื่อง: อ่าน, รวม/แยก, บีบอัด, แก้ไข, ส่งออก/นำเข้า Word-PowerPoint-Excel-รูปภาพ, ป้องกัน/ปลดล็อก, ปิดบังข้อความ และงานอื่นๆ

จุดต่างจากเว็บอย่าง iLovePDF (ที่ผู้ใช้ยกเป็นตัวอย่าง): ไม่ต้องอัปโหลด (เอกสารลับอยู่ในเครื่อง), ไม่จำกัดขนาด/จำนวนไฟล์, ใช้ออฟไลน์ได้, มีตัวอ่านและตัวแก้ไขในโปรแกรมเดียว

**ไม่อยู่ในขอบเขต (ตัดสินใจไว้ก่อน บอกตรงๆ ว่าไม่ทำ):**
- ถอดรหัสผ่าน PDF ด้วยการเดา/brute force (ดูหัวข้อ 4.7)
- แปลง HTML เป็น PDF (ต้องใช้เอนจินเว็บ ซึ่งขัดกฎ "ไม่ใช้ WebView")
- การลงนามดิจิทัลแบบ PAdES/ใบรับรองรัฐ ในรุ่นแรก (มีแค่ลายเซ็นแบบภาพ; ลายเซ็นดิจิทัลอยู่ Phase 7 และต้องตัดสินใจเรื่องใบรับรอง)
- คลาวด์ การทำงานร่วมกันแบบออนไลน์ บัญชีผู้ใช้

## 3. ฟีเจอร์อื่นๆ ("ฯลฯ") ที่เสนอ

จัดกลุ่มตามความคุ้ม (อ้างอิงเครื่องมือที่เว็บ PDF ทั่วไปมี):

**จัดการหน้า:** หมุน, ลบ, เรียงใหม่, แทรกหน้าว่าง, ตัดขอบ (crop), ดึงบางหน้าออก, ใส่เลขหน้า / header / footer / Bates number, ลายน้ำ (ข้อความ/รูป), flatten (ยุบ annotation/ฟอร์มให้เป็นเนื้อหา)
**อ่านและอ้างอิง:** ค้นหาทั้งเอกสาร, highlight / underline / strikethrough / comment, ตัวเลื่อนความสว่าง/โหมดมืด, จำหน้าที่อ่านล่าสุด
**ฟอร์ม:** กรอก AcroForm, ลายเซ็นแบบภาพ (วาด/พิมพ์/รูป)
**OCR:** แปลงสแกนเป็น PDF ค้นหาได้ (ภาษาไทย + อังกฤษ) ใช้ Tesseract แบบออฟไลน์ โมเดลภาษาต้องกดปุ่มดาวน์โหลดเองตามกฎของโปรเจกต์ (ไม่โหลดเอง)
**เปรียบเทียบ:** เทียบ 2 ไฟล์ (ข้อความ/ภาพ) แสดงส่วนที่ต่าง
**ข้อมูลไฟล์:** แก้ metadata, ดู/ลบไฟล์แนบ, ซ่อม PDF ที่เสียเล็กน้อย (ผ่านการสร้างโครงสร้างใหม่ของ qpdf)
**แปลงรูปแบบ:** รูป → PDF, PDF → PDF/A (ทำทีหลังและเป็นแบบ "ตรวจแล้วรายงาน" ไม่ใช่รับรองมาตรฐาน; ต้องตรวจ)
**งานเป็นชุด (batch):** เลือกโฟลเดอร์ แล้วบีบอัด/ใส่ลายน้ำ/ใส่รหัสทั้งหมดในครั้งเดียว มีรายงานผลต่อไฟล์
**สแกนเข้า PDF:** จากสแกนเนอร์ (Windows WIA) ทำใน Phase 7 ถ้ามีเวลา

## 4. สถาปัตยกรรมและการเลือกเทคโนโลยี

### 4.1 หลักการ
- แยกเป็นไลบรารีแบบ static ต่อโฟลเดอร์ เหมือน Video Editor (`core`, `pdfengine`, `document`, `render`, `edit`, `tools`, `convert`, `security`, `ocr`, `app`, `ui`) ทิศทางพึ่งพาลงล่างเท่านั้น
- ตัวห่อหุ้มเอนจิน (`pdfengine`) เป็นชั้นเดียวที่แตะไลบรารี PDF ภายนอก เพื่อสลับตัวได้และเขียนเทสต์ได้
- งานหนัก (เรนเดอร์, บีบอัด, OCR, แปลง) ทำนอก UI thread มี progress และยกเลิกได้ทุกงาน
- ไม่แก้ไฟล์ต้นฉบับ: บันทึกแบบ "บันทึกเป็น" หรือเขียนไฟล์ชั่วคราวแล้วค่อยแทนที่แบบ atomic (มี `fileutils::writeAtomic` อยู่แล้ว) และมี autosave/กู้คืนเหมือน Video Editor
- แก้ไขทุกอย่าง undo/redo ได้ (undo stack ระดับการกระทำ)
- ข้อความทุกอย่างใช้ `qsTr` + แปลไทย; ใช้ `AppText` และกฎ `ThaiMetrics` เหมือน Video Editor (ภาษาไทยกับอังกฤษขนาด/ระยะบรรทัดเท่ากัน)

### 4.3 การบีบอัด (ข้อ 3) ทำอย่างไรให้ได้ผลจริง
ขั้นตอนเป็นชั้น เรียงตามปลอดภัยไปหาแรง ผู้ใช้เลือกระดับ (ต่ำ/กลาง/สูง/กำหนดเอง):
1. เขียนโครงสร้างใหม่ + object streams + deflate สูงสุด (ไม่ทำให้คุณภาพเปลี่ยน)
2. ลบ object ที่ไม่มีใครอ้างถึง, metadata ซ้ำ, thumbnail ฝัง, ข้อมูล editor เดิม
3. ฟอนต์: ตรวจฟอนต์ที่ฝังซ้ำ/subset ที่ทำได้โดยไม่เสียเสมอ
4. ภาพ: ลด DPI ตามเป้า (เช่น 150/110/72), แปลงเป็น JPEG คุณภาพที่เลือก, ข้ามภาพที่เล็กอยู่แล้ว, **ไม่ทำให้ไฟล์ใหญ่ขึ้น** (ถ้าผลใหญ่กว่าเดิมให้เก็บของเดิม)
5. linearize (เปิดบนเว็บเร็ว)
แสดงผลเป็นตัวเลขจริง ก่อน/หลัง (ขนาด, % ที่ลด, จำนวนภาพที่ลดคุณภาพ) และไม่เคลมว่า "คุณภาพสูงสุด" ถ้าไม่ได้วัด; มี preview เทียบหน้าตัวอย่างก่อนบันทึก

### 4.4 การแก้ไข PDF (ข้อ 4) ความจริงที่ต้องบอกผู้ใช้
- **เพิ่มสิ่งใหม่** (ข้อความ, รูป, รูปร่าง, ลายมือ, หมายเหตุ/ไฮไลต์): ทำได้ดี เก็บเป็น annotation หรือเนื้อหาหน้าตามที่ผู้ใช้เลือก (แก้ภายหลังได้ถ้าเป็น annotation; flatten เมื่อต้องการถาวร)
- **แก้ข้อความเดิมที่อยู่ใน PDF**: PDF ไม่ได้เก็บ "ย่อหน้า" แต่เก็บตัวอักษรที่วางตำแหน่งแล้ว การแก้ข้อความเดิมจึงทำได้เฉพาะบรรทัดเดียว/ข้อความที่ฟอนต์ฝังครบตัวอักษร และมักต้องฝังฟอนต์ใหม่; ภาษาไทยยากกว่า (ข้อ 4.5) ทำเป็น Phase ท้ายของการแก้ไข และติดป้ายสถานะ "ทดลอง / จำกัด" จนกว่าจะมีเทสต์ครอบคลุม
- แก้ขนาด/ฟอนต์/สีของสิ่งที่ผู้ใช้เพิ่มเองได้เต็มรูปแบบ (อยู่ใน model ของโปรแกรม)
- ฟอนต์: ใช้ฟอนต์ที่โปรแกรมมี (Inter, Noto Sans Thai) + ฟอนต์ในเครื่อง ผู้ใช้ต้องมีสิทธิ์ฝังฟอนต์นั้น (แสดงคำเตือนถ้าฟอนต์ห้ามฝัง)

### 4.5 ภาษาไทยคือจุดเสี่ยงหลัก
เพิ่มข้อความไทยลง PDF ต้อง shaping (วางสระบน/ล่าง วรรณยุกต์) แล้วเขียนเป็นตำแหน่งตัวอักษรเอง พร้อมให้ **ข้อความยังค้นหา/คัดลอกเป็นไทยที่ถูกต้อง** (ToUnicode map). ต้องมีเทสต์ภาพ+เทสต์ดึงข้อความกลับ ไม่ใช่เช็คแค่ว่าไฟล์เปิดได้

### 4.6 ส่งออก/นำเข้า Office (ข้อ 5, 6) ตรงไปตรงมา
**PDF → รูปภาพ:** PNG/JPEG/TIFF, เลือกหน้า/DPI — ทำเต็มและเทสต์ด้วยพิกเซลได้
**PDF → Word/PowerPoint/Excel:** ไม่มีวิธีที่ถูกต้อง 100%; แผนคือ
- Word (.docx): ดึงข้อความ+ลำดับอ่าน+รูป+ตารางแบบง่าย เขียน OOXML เอง (ไม่ผ่านโปรแกรมอื่น) เค้าโครงซับซ้อน/คอลัมน์/ฟอร์มจะไม่เหมือนเดิม
- PowerPoint (.pptx): หนึ่งหน้า = หนึ่งสไลด์ ภาพหน้าเป็นพื้นหลัง + กล่องข้อความที่ดึงได้ (โหมด "แก้ไขข้อความได้" / โหมด "เหมือนต้นฉบับ = ภาพอย่างเดียว")
- Excel (.xlsx): ตรวจตารางจากเส้น/การจัดแนวตัวอักษร ผลขึ้นกับเอกสาร ติดป้าย "ประมาณการ" ในผลลัพธ์
- สแกน (ไม่มีข้อความ) ต้องผ่าน OCR ก่อน
- ทุกการส่งออกแสดง "รายงานความเหมือน" (สิ่งที่ดึงไม่ได้/ข้ามไป) และเทสต์ด้วยเอกสารจริงวัดจากข้อความที่ได้กลับมา
**Word/PowerPoint/Excel → PDF:** โปรแกรมแถมตัวแปลง Office เองไม่ได้โดยไม่เสี่ยงสัญญาอนุญาต/ขนาดใหญ่; แผน:
1. ถ้าเครื่องมี Microsoft Office: สั่งผ่าน COM automation (ใช้โปรแกรมของผู้ใช้ ต้องมีสิทธิ์ใช้งานอยู่แล้ว)
2. ถ้ามี LibreOffice: เรียกแบบ headless
3. ถ้าไม่มีทั้งสอง: ปุ่มเป็น "ต้องติดตั้ง Microsoft Office หรือ LibreOffice" (ใช้ป้ายสถานะ `unsupported`/`modelRequired` ตามกฎ UI) ไม่แกล้งทำ
รูปภาพ (JPG/PNG/TIFF/BMP) → PDF ทำในตัวเต็ม (จัดขนาดกระดาษ ระยะขอบ ทิศทาง)

### 4.7 ป้องกัน / ปลดล็อก (ข้อ 7)
- ป้องกัน: รหัสเปิดไฟล์ + รหัสเจ้าของ + จำกัดสิทธิ์ (พิมพ์/คัดลอก/แก้ไข) ด้วย AES-256 (qpdf) แสดงคำเตือนว่าสิทธิ์จำกัดบางอย่างโปรแกรมอื่นอาจไม่ปฏิบัติตาม
- ปลดล็อก: **ต้องใส่รหัสที่ถูกต้อง** แล้วบันทึกเป็นไฟล์ที่ไม่มีรหัส/ไม่มีข้อจำกัด; ไฟล์ที่มีแค่รหัสเจ้าของ (เปิดอ่านได้โดยไม่ต้องใส่รหัส) ปลดข้อจำกัดได้เฉพาะไฟล์ที่ผู้ใช้เป็นเจ้าของหรือมีสิทธิ์ — มีข้อความยืนยันก่อนทำ
- **ไม่ทำการเดารหัส/ถอดรหัสแบบ brute force** (เสี่ยงใช้ผิดกฎหมาย/ละเมิดสิทธิ์ และไม่อยู่ใน scope)
- รหัสผ่านไม่ถูกเขียนลงล็อกหรือไฟล์ตั้งค่า ไม่เก็บในหน่วยความจำนานเกินจำเป็น

### 4.8 ปิดบังข้อความ - redaction (ข้อ 8)
สำคัญที่สุดเรื่องความถูกต้อง: การวางกล่องดำทับ **ไม่ใช่การปิดบัง** เพราะข้อความยังอยู่ในไฟล์
- เลือกพื้นที่/ค้นหาคำ/รูปแบบ (regex พร้อม preset: เลขบัตรประชาชนไทย 13 หลัก, เบอร์โทร, อีเมล, เลขบัญชี) → ทำเครื่องหมาย → ตรวจ → "ใช้ redaction"
- เมื่อใช้: ลบตัวอักษรออกจาก content stream, ครอบพื้นที่ภาพด้วยการเขียนพิกเซลใหม่ (rasterize เฉพาะบริเวณ), ลบ annotation/ข้อความที่ซ่อน/metadata/ไฟล์แนบ/thumbnail ที่เกี่ยวข้อง, เขียนไฟล์ใหม่ (ไม่เก็บ incremental update เดิม)
- **ตรวจสอบหลังทำ**: ดึงข้อความของเอกสารที่ได้แล้วต้องไม่พบข้อความที่ลบ; มีเทสต์อัตโนมัติสำหรับข้อนี้โดยเฉพาะ (เป็นเกณฑ์ผ่าน/ไม่ผ่านของ Phase 6)

## 5. การเชื่อมกับชุดโปรแกรม DriveVault
ต้องทำตามสัญญาใน `docs/suite-integration.md` (ห้ามเปลี่ยนสัญญา ต้องตามให้ครบ):
- ติดตั้งที่ `C:\Program Files\DriveVault\Common\DriveVault PDF Pro` (ต่อผู้ใช้: `%LOCALAPPDATA%\Programs\DriveVault\...`) รีจิสทรี `Software\DriveVault\Products\PdfPro` + `product.json` (id `drivevault.pdf` ตรงกับแคตตาล็อกใน Master Pro; accent `#EF4444`)
- ตัวติดตั้ง Inno Setup สร้าง `AppId` ใหม่ **ครั้งเดียวแล้วห้ามเปลี่ยน**; แถม/รันตัวติดตั้ง Master Pro ก่อนเมื่อยังไม่มีหรือเก่ากว่า; version resource `CompanyName = DriveVault`, `ProductName = DriveVault PDF Pro`
- ผ่านเกต `package.ps1`: ตรวจ clean-machine import, license audit (ทุกไฟล์ต้องมีเจ้าของ/สัญญาอนุญาต ต้องเพิ่มกฎของ PDFium/qpdf/HarfBuzz/ ฯลฯ), ประกาศบุคคลที่สาม (`THIRD-PARTY-NOTICES.txt`)
- Master Pro: เปลี่ยนป้ายจาก "เร็วๆ นี้" เป็นสถานะจริงเมื่อมีตัวติดตั้งใช้งานได้เท่านั้น
- ไม่มีอะไรดาวน์โหลดเอง (รวมโมเดล OCR) นอกจากผู้ใช้กดปุ่ม
- เปิดไฟล์ `.pdf` ด้วย PDF Pro ผ่านการตั้ง "Open with" ที่ผู้ใช้เลือกเอง (ไม่แย่งเป็นโปรแกรมเริ่มต้นเอง) - ต้องตัดสินใจ

## 6. แผนเป็นเฟส (milestone) พร้อมเกณฑ์ผ่าน

| เฟส | ขอบเขต | เกณฑ์ผ่านหลัก (วัดได้) | สถานะ |
|---|---|---|---|
| 0 | ตัดสินใจเรื่องเอนจิน/สัญญาอนุญาต, สร้างโครงโปรเจกต์ + แบบ UI, ต้นแบบเปิดไฟล์ | เลือกไลบรารีและผ่าน license audit; เปิดและเรนเดอร์ PDF ตัวอย่าง 10 ไฟล์ได้ | ยังไม่เริ่ม |
| 1 | **ตัวอ่าน**: เปิด, ซูม, โหมดหน้า, ค้นหา, เลือก/คัดลอก, bookmark, thumbnail, แท็บ, พิมพ์, ไฟล์ที่มีรหัส, ไฟล์ใหญ่ | เปิดไฟล์ 500 หน้าแล้วหน้าแรกขึ้นเร็วและหน่วยความจำไม่โตเกินกำหนด (ตั้งตัวเลขเป้าหมายหลังต้นแบบ); ข้อความไทยที่เลือก/คัดลอกถูกต้อง | ยังไม่เริ่ม |
| 2 | **รวม/แยก/จัดหน้า**: ลากเรียง, แยกหลายแบบ, หมุน/ลบ/แทรก/ตัดขอบ, undo | ผลรวมมีจำนวนหน้าและลำดับถูกต้อง เปิดด้วยตัวอ่านอื่นได้ (ตรวจด้วย qpdf --check) | ยังไม่เริ่ม |
| 3 | **บีบอัด/เพิ่มประสิทธิภาพ**: ระดับ, DPI, preview, รายงานผล, linearize, batch เบื้องต้น | ชุดไฟล์ทดสอบ (สแกน, ภาพหนัก, ข้อความล้วน) ลดขนาดตามที่รายงานจริง ไม่มีไฟล์ใหญ่ขึ้น และหน้าตาเทียบพิกเซลอยู่ในเกณฑ์ที่ตั้ง | ยังไม่เริ่ม |
| 4 | **แก้ไข**: ข้อความ/รูป/รูปร่าง/ปากกา/ไฮไลต์/คอมเมนต์/ฟอร์ม/ลายเซ็นภาพ; ลายน้ำ/เลขหน้า; แก้ข้อความเดิมแบบจำกัด (ทดลอง) | เพิ่มข้อความไทย+อังกฤษแล้วบันทึก เปิดด้วยตัวอ่านอื่นและดึงข้อความกลับได้ตรง; undo/redo ทุกการกระทำ; autosave กู้คืนได้ | ยังไม่เริ่ม |

เฟส 1-3 ให้ผู้ใช้ได้โปรแกรมที่ใช้งานได้จริงเร็ว (อ่าน + รวม/แยก + บีบอัด) จึงเสนอให้ออกรุ่น 0.x หรือ 1.0.0 หลังเฟส 3 ได้ถ้าเจ้าของต้องการ (ตัดสินใจภายหลัง) ส่วนเฟส 4-7 ออกเป็นรุ่นย่อยตามลำดับ

## 7. ชุดทดสอบ (แนวทาง ตามกฎของโปรเจกต์: ใช้ข้อมูลจริง วัดผลจริง)
- ไฟล์ทดสอบสร้างเองในเทสต์ (ข้อความไทย/อังกฤษ, ภาพ, ฟอร์ม, สแกน, ไฟล์มีรหัส, ไฟล์ใหญ่หลายร้อยหน้า) ไม่พึ่งไฟล์ลิขสิทธิ์ภายนอก
- ตรวจผลเป็นข้อมูล: จำนวนหน้า, ข้อความที่ดึงกลับ, ขนาดไฟล์ก่อน/หลัง, พิกเซลของหน้าที่เรนเดอร์ (เทียบเกณฑ์), `qpdf --check`
- เทสต์ความปลอดภัยของ redaction เป็นเกณฑ์บังคับ (ดู 4.8)
- เทสต์ UI offscreen แบบเดียวกับ `tst_ui_flow` (ล้มทันทีเมื่อมีคำเตือน QML) และเทสต์ประสิทธิภาพเปิดไฟล์ใหญ่
- ทุกเทสต์ต้องเงียบ (`DV_NO_AUDIO=1`) และไม่แตะไฟล์/ข้อมูลของผู้ใช้
- ไม่ทดสอบตัวติดตั้ง/ถอนติดตั้งโดย agent ตามกฎข้อ 3a

## 8. ความเสี่ยงหลัก และวิธีรับมือ

| ความเสี่ยง | ผลกระทบ | วิธีรับมือ |
|---|---|---|
| แก้ข้อความเดิมใน PDF (โดยเฉพาะภาษาไทย) ทำได้ไม่ดี | ผู้ใช้คาดหวังเหมือน Acrobat | ติดป้าย "ทดลอง/จำกัด" ตรงๆ, ทำสิ่งที่ทำได้ดีก่อน (เพิ่มสิ่งใหม่), เก็บเป็นเฟสท้าย |
| PDF→Word/Excel เค้าโครงเพี้ยน | ผู้ใช้ผิดหวัง/เข้าใจผิดว่าบั๊ก | รายงานความเหมือนทุกครั้ง, อธิบายข้อจำกัดในคู่มือ, ไม่โฆษณาเกินจริง |
| สัญญาอนุญาตของไลบรารี | แจกจ่ายไม่ได้ | ตรวจใน Phase 0 ผ่าน license audit ก่อนเขียนโค้ดจริง, เลี่ยง AGPL/GPL |
| Redaction ไม่สะอาด | ข้อมูลลับรั่ว (ผลร้ายแรง) | ทำ redaction จริง + ตรวจหลังทำ + เทสต์บังคับ + ข้อความเตือนผู้ใช้ให้ตรวจก่อนส่ง |
| ไฟล์ใหญ่/สแกนหนัก กินหน่วยความจำ | ค้าง/ปิดตัว | เรนเดอร์ทีละหน้า+แคช tile, memory budget, งานหนักนอก UI thread, ทดสอบไฟล์ใหญ่ |
| การเดารหัสผ่าน/ละเมิดสิทธิ์ | ปัญหากฎหมาย | ไม่ทำ (4.7) |
| Office→PDF ต้องพึ่งโปรแกรมอื่น | บางเครื่องใช้ไม่ได้ | บอกชัดเจนและมีป้ายสถานะ ไม่แกล้งทำ |
| ขนาดตัวติดตั้งใหญ่ (Qt + PDFium + OCR) | ดาวน์โหลดช้า | แยกโมเดล OCR ให้ดาวน์โหลดเมื่อต้องการ, วัดขนาดจริงตอน Phase 8 |
| ไม่ได้ลงนามโค้ด (เหมือนโปรแกรมอื่น) | Windows เตือน | เป็นข้อค้างอยู่ของเจ้าของ (ใบรับรอง) |

## 9. สิ่งที่ต้องให้เจ้าของตัดสินใจก่อนเริ่ม Phase 0

1. **เอนจินอ่าน/เรนเดอร์**: PDFium (แนะนำ) หรือ Qt PDF (ถ้าผ่านเกตสัญญาอนุญาต)
2. **ขอบเขตรุ่นแรก**: ออกรุ่นแรกหลังเฟส 3 (อ่าน + รวม/แยก + บีบอัด) หรือรอจนครบเฟส 6
3. **Office → PDF**: ยอมรับแนว "ใช้ Microsoft Office/LibreOffice ที่ผู้ใช้มีอยู่" หรือไม่ (ไม่แถมตัวแปลงมาเอง)
4. **PDF → Word/PowerPoint/Excel**: ยอมรับว่าเป็นแบบ "พยายามรักษาเค้าโครง + รายงานความเหมือน" หรือไม่
5. **ลายเซ็นดิจิทัล**: ต้องการในรุ่นแรกไหม (ต้องมีใบรับรอง/ข้อกฎหมาย) หรือเริ่มจากลายเซ็นแบบภาพ
6. **OCR**: ต้องการไหม และยอมให้ดาวน์โหลดโมเดลภาษาเมื่อผู้ใช้กดปุ่มหรือไม่
7. **ตั้งเป็นโปรแกรมเปิด .pdf ของ Windows**: ให้ผู้ใช้เลือกเอง (แนะนำ) หรือเสนอตอนติดตั้ง
8. **ชื่อและสี**: ใช้ชื่อ "DriveVault PDF Pro" และสีแดง `#EF4444` ตามที่มีใน Master Pro อยู่แล้ว (ยืนยัน)

## 10. ขั้นต่อไปที่แนะนำ
ถ้าเจ้าของอนุมัติ: เริ่ม Phase 0 ด้วยการตรวจสัญญาอนุญาต PDFium / qpdf / Qt PDF จากไฟล์ LICENSE จริงของเวอร์ชันที่จะใช้ ขอสิทธิ์ดาวน์โหลดเครื่องมือก่อนตามกฎ ("ดาวน์โหลดอะไร จากที่ไหน ขนาดเท่าไร") แล้วทำต้นแบบเปิด PDF 10 ไฟล์เพื่อวัดความเร็ว/หน่วยความจำและกำหนดเป้าหมายตัวเลขของ Phase 1
